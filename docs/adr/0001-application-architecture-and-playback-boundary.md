# 采用 AppKit 外壳、SwiftUI 内容与隔离的播放边界

应用采用 AppKit 管理主窗口、全屏、播放画布、屏上控制器层级和画中画桥接，并将播放列表、设置、媒体信息与恢复流程作为 SwiftUI 内容嵌入。播放协调层是用户可见播放状态的唯一写入者，拥有播放列表推进、续播、随机轮次、重复方式和轨道规则；它只依赖窄而稳定的 `PlaybackEngine` 端口，不接触 libmpv 命令或属性。libmpv 适配器在独立串行执行上下文中运行，并以类型化事件将状态送回 `MainActor` 上的播放协调层。

持久状态使用 SQLite，但应用层只依赖自有存储接口；存储事务、安全作用域书签解析、文件遍历和媒体探测均与 UI 及播放引擎隔离。领域策略保持确定且可注入时间、随机数和外部端口，以便使用内存存储与假播放器进行测试；SQLite、文件访问和 libmpv 适配器分别通过契约测试与集成测试验证。

未来逐帧、视频色彩控制和 AB 循环通过独立能力接口静态装配，波形生成通过单独的媒体分析边界提供。应用不建设动态插件系统、不暴露通用 mpv 命令通道，也不采用 AVFoundation 与 libmpv 双引擎运行时。原生画中画和 App Store 打包仍须通过后续原型门槛；门槛失败时替换适配器或调整功能范围，而不改变上层领域模型。

## 考虑过的方案

- 纯 SwiftUI 会让视频渲染、全屏覆盖层和画中画等窗口级能力持续穿透框架边界。
- 纯 AppKit 会给状态驱动的播放列表与设置界面增加不必要的样板代码。
- 包揽播放、列表、持久化和引擎命令的单体播放器管理器会混淆领域所有权，并使测试依赖真实引擎。
